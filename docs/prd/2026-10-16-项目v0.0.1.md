## 1. 产品概述

### 1.1 背景与痛点

在开发复杂的 LLM Agent（特别是具备 ReAct 循环或多智能体协同系统）时，开发者面临两大核心痛点：

- **被动观测的无奈（"盲飞"）**：传统 APM（如 Langfuse、Langsmith）架构过重，需要 Docker/Postgres，且只能在 Agent 跑完后进行被动查看，无法阻止 Agent 运行时陷入死循环（Loop）导致 Token 费用暴涨。
- **高危工具调用失控**：在本地调试涉及写数据库、发邮件、调用金融 API 等高危工具时，开发者不敢用真实环境测试，缺乏一种像传统编程语言（Java/Go）一样的"断点（Breakpoint）"控制机制。

### 1.2 产品定位

MicroAgent-Lens 是一款专为 Agent 开发者打造的 Pure Python、零配置、本地自托管的 Agent 运行时调试工作台（Debugger）。

> **核心定位：控制优先、开发期工具（dev-time tool），对标 debugger 而非 APM。**

- 核心口号：*Stop tracing after crashes. Control your agents in real-time.*（告别崩溃后的追溯，实时掌控你的智能体。）

### 1.3 差异化：为什么不是又一个观测平台

市面 Agent 观测工具已很多（Langfuse、Langsmith、Helicone 等），但它们同属一个产品类别——**事后可观测性（observability）**：数据跑完后才汇总到平台，只能被动分析，无法实时干预。

MicroAgent-Lens 的壁垒建立在 Langfuse **做不了**的维度上——**运行时控制（control/intervention）**。

| 维度 | 传统 APM | MicroAgent-Lens |
|---|---|---|
| 产品类别 | 事后可观测性 | 运行时控制 |
| 数据流 | 跑完才汇总到平台 | 执行中实时干预 |
| 护城河 | 数据分析 + 团队协作 + 企业集成 | 熔断 + 人机协同断点 |
| 定位边界 | 运行期平台 | 开发期本地工具 |

类比：编程语言的历史里，`print`/logging 从未替代 `breakpoint`/debugger。**Agent 开发目前正处于"只有 print、没有 debugger"的阶段**——这是本项目的空位，真正的对标物是 pdb / gdb / IDE 断点调试器。

### 1.4 目标用户

- 开发 LLM Agent 的开发者（自研循环或基于 LangChain/LlamaIndex 等框架）。
- 使用场景：**本地开发调试**（非生产、非 CI），单人、即时、交互式。

## 2. 使用场景

### 2.1 三个核心场景

| 场景 | 传统 APM 现状 | MicroAgent-Lens 价值 | 类别 |
|---|---|---|---|
| A. 死循环烧钱 | 事后告知"这次花了 $50" | 当场熔断、实时止损 | 控制（壁垒） |
| B. 高危工具不敢跑 | 只能 mock 或硬上真环境 | 断点逐步"看参数确认再放行" | 控制（壁垒） |
| C. ReAct 轨迹难读 | 扁平 span，看不出推理过程 | 专用 trace tree 结构化 Thought→Action→Observation | 观测（体验加成） |

### 2.2 端到端使用流程

以自研 ReAct agent（工具：`execute_sql` / `send_email`）为例：

**① 安装**
```bash
pip install microagent-lens
```

**② 开看板（一条命令，单独终端挂着）**
```bash
lens serve          # 本地起服务，浏览器自动打开 localhost:7878
```

**③ 给工具函数加装饰器（唯一代码改动，函数体一行不改）**
```python
from lens import bind_tool

@bind_tool                      # 普通工具：只记录
def execute_sql(sql: str) -> list[dict]:
    return db.query(sql)

@bind_tool(suspend=True)        # 高危工具：命中即挂起，等人放行
def send_email(to: str, subject: str, body: str):
    smtp.send(to, subject, body)

# ↓ 原 agent 循环完全不动 ↓
```

**④ 照常跑**：`python my_agent.py`

**⑤ 运行时交互**
- Agent 跑到 `send_email` → 网页弹框（显示当前 prompt + 工具 + 参数）→ 开发者点【放行】或【拒绝】。
- 死循环重复调用同一工具 → 熔断告警，agent 抛 `AgentLoopException` 停止，Token 止损。
- 全程右侧 trace 树实时生长，跑完可回看。

## 3. 功能需求

### 3.1 模块一：Zero-Config SDK 探针

- **需求描述**：开发者通过一行代码或命令行，即可无侵入地拦截 LLM 的输入输出及工具调用。
- **具体规则**：
  - 支持以 Python 装饰器（Decorator）形式挂载到自定义工具函数上：`@lens.bind_tool()`。
  - 自动管理 Session 状态，利用 Python 的 `contextvars` 维持多线程/异步环境下的 Trace 树状上下级关系。
  - 免部署设计：SDK 收集的数据通过本地 HTTP 发送给本地轻量存储，不需要用户配置任何外部数据库。

### 3.2 模块二：Active Guardrails（主动防御与断点引擎）

这是本项目的核心技术壁垒。

#### 3.2.1 滑窗状态死循环熔断器（Loop Breaker）

- **原理**：维护一个滑动窗口，记录当前 Session 最近 N 次的 Action（工具名）和 Arguments（参数）。
- **规则**：若连续 3 次调用的工具名称完全一致，且参数的文本相似度（编辑距离或 Jaccard 相似度）大于 90%，触发熔断拦截。
- **动作**：中断执行，向主程序抛出自定义异常 `AgentLoopException`，防止 Token 持续空转烧钱。

#### 3.2.2 人机协同高危断点拦截（Active Breakpoint）

- **原理**：工具命中 SUSPEND 标记时，SDK 阻塞等待开发者决策（放行/拒绝）。
- **规则**：开发者可在前端 UI 或配置文件中，将特定工具（如 `execute_sql`、`send_email`）标记为 SUSPEND（暂停）。
- **动作**：
  1. Agent 命中该工具时，SDK 拦截执行，向看板发送挂起信号。
  2. SDK 阻塞当前执行，等待开发者决策。
  3. 网页端弹出交互框，显示当前的 Prompt、准备调用的工具及参数。
  4. 开发者点击【放行】→ 继续执行；点击【拒绝】→ **返回失败结果**（而非抛异常），让 Agent 以为工具执行失败、自行走错误分支继续推理。

> 设计说明：断点的"拒绝"返回失败结果而非抛异常，是本产品"人机协同"的精髓——debugger 的语义是"逐步替 Agent 做决定、看它如何应变"，而非杀掉 Agent。

### 3.3 模块三：Local Visual Dashboard（本地可视化工作台）

- **需求描述**：一个纯 Python 编写的极简、高颜值暗黑模式仪表盘。
- **具体规则**：
  - **主页/列表页**：展示历史调试的 Session 列表、成功/失败状态、Token 总消耗、运行耗时。
  - **轨迹详情页（Agent Trace Tree）**：专门优化 ReAct 结构的树状视图，清晰区分 Thought（思考）→ Action（工具调用）→ Observation（工具返回）。
  - **断点控制面板**：提供开关，允许动态勾选哪些工具需要开启"执行前暂停"断点。

## 4. 架构与关键设计决策（需求层面）

### 4.1 进程分离架构

```
[Agent 进程 —— 任意语言]        [Lens 后端 —— 纯 Python]        [WebUI —— 浏览器]
  Go / TS / Py agent             FastAPI + SQLite + 决策引擎       HTML/JS
```

收集、存储、熔断判定、断点挂起、WebUI 全在后端，**与 Agent 语言无关**；依赖语言的只有"探针"这一层。

### 4.2 智能放后端，SDK 变薄协议 client

熔断判定与断点挂起决策统一放后端；SDK 只做"发 HTTP + 阻塞等响应 + 抛异常/返回失败"。

- **理由**：一份逻辑跨语言共享，每种语言的 SDK 退化为几十行模板代码，未来加 Go/TS 无需重写核心逻辑。

### 4.3 统一决策端点（概念）

Loop Breaker 与 Active Breakpoint 统一为同一决策流程：SDK 在**每次工具调用前**同步请求后端，后端返回三类决策——`allow`（放行）、`reject:loop`（熔断）、`reject:human`（人类拒绝）。挂起场景下后端延迟响应，直到开发者在网页做出选择。

> 注：具体 endpoint 清单与消息结构（JSON schema）属技术设计，本文档不展开，留待后续设计文档。

### 4.4 跨语言策略

- MVP 仅实现 **Python SDK**（装饰器是语法糖，符合 Pure Python 定位）。
- 协议从第一天起即语言无关（HTTP/JSON），未来支持 Go/TS 只需加一个薄 client，**后端零改动**。
- Go/TS 探针形态：Go 用 wrapper/显式埋点，TS 用装饰器或显式埋点，底层同一协议。

## 5. 非功能需求

- **零配置**：`pip install` + 一条 `lens serve` 命令即用，无需 Docker/Postgres。
- **降级策略**：看板未启动时 Agent 必须照常运行，SDK 静默降级，绝不影响 Agent 主流程。
- **本地自托管**：数据本地存储，不依赖外部服务。
- **低侵入**：接入成本 = 一行 import + 每个工具一个装饰器，函数体不改。

## 6. MVP 范围与版本规划

### 6.1 MVP 做

| 优先级 | 内容 | 定位 |
|---|---|---|
| 核心 | Active Guardrails（Loop Breaker + Active Breakpoint） | 砸力气的地方，壁垒所在 |
| 支撑 | 最小可用 SDK 探针 | 喂给熔断器/断点即可，不做全量 tracing |
| 展示 | 够用的控制面板 + trace 树 | 暗黑高颜值是加分项，非门槛 |

### 6.2 MVP 不做

多租户、权限、生产高可用、团队共享——本项目是 dev-time 本地工具，以上一律不在范围内。

### 6.3 版本规划

- `0.1.0` = MVP（首个可用的控制型调试器）。
- `0.x` 阶段 API 随时可变，`1.0.0` 为远期稳定版。

---

## 7. 未来规划（非 MVP）

- **框架适配器**：LangChain/LlamaIndex callback 自动采集 Thought 与 LLM I/O（当前靠手动 `log_thought()` 埋点）。
- **Go / TS SDK**：薄协议 client，后端零改动。
- **观测增强**：更丰富的 trace 分析、成本聚合等（在"控制"站稳后向"观测"延伸）。
