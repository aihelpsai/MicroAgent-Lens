# MicroAgent-Lens 定位与架构决策纪要

- 日期：2026-10-16
- 类型：调研 / 讨论结论
- 状态：定位与核心架构已定，待细化通信协议
- 依据文档：`docs/prd/2026-10-16-项目v0.0.1.md`

---

## 1. 背景

LLM Agent 开发的两大痛点（见 `prd.md`）：

1. **被动观测（"盲飞"）**：传统 APM（Langfuse / Langsmith）架构重、只能事后查看，无法阻止 Agent 运行时陷入死循环导致 Token 费用暴涨。
2. **高危工具调用失控**：本地调试写库 / 发邮件 / 金融 API 等高危工具时不敢用真实环境，缺传统语言（Java/Go）那样的"断点"控制机制。

本纪要讨论的核心问题：市面 Agent 观测工具已很多（Langfuse 等），MicroAgent-Lens 的差异化定位与 MVP 边界是什么，以及"怎么用"。

---

## 2. 核心定位（已确认）

> **控制优先、开发期工具（dev-time tool），对标 debugger 而非 APM。**

- 不做"事后可观测平台"（那是 Langfuse 的主场），做**运行时干预（control/intervention）**。
- 真正的对标物是 **pdb / gdb / IDE 断点调试器**，而非 Langfuse。
- 本质是：编程语言的历史里，`print`/logging 从未替代 `breakpoint`/debugger；**Agent 开发目前正处于"只有 print、没有 debugger"的阶段**，这是本项目的空位。

Slogan（沿用 PRD）：*Stop tracing after crashes. Control your agents in real-time.*

---

## 3. 差异化：观测 vs 控制

| 维度 | 传统 APM（Langfuse 等） | MicroAgent-Lens |
|---|---|---|
| 产品类别 | 事后可观测性（observability） | 运行时控制（control） |
| 数据流 | 跑完才汇总到平台 | 执行中实时干预 |
| 护城河 | 数据分析 + 团队协作 + 企业集成 | 熔断 + 人机协同断点 |
| 定位边界 | 运行期平台 | 开发期本地工具 |

结论：**在"观测"维度上无法与 Langfuse 竞争；壁垒必须建立在 Langfuse 做不了的"控制"上。**

---

## 4. 三个真实价值场景

| 场景 | 传统 APM 现状 | MicroAgent-Lens 价值 | 类别 |
|---|---|---|---|
| A. 死循环烧钱 | 事后告知花费 | 当场熔断、实时止损 | 控制（壁垒） |
| B. 高危工具不敢跑 | 只能 mock 或硬上真环境 | 断点逐步"看参数确认再放行" | 控制（壁垒） |
| C. ReAct 轨迹难读 | 扁平 span，看不出推理 | 专用 trace tree 结构化 Thought→Action→Observation | 观测（体验加成） |

- A、B 是壁垒，C 是加分项。

## 5. 端到端使用流程

以自研 ReAct agent（工具：`execute_sql` / `send_email`）为例：

**① 安装**
```bash
pip install microagent-lens
```

**② 开看板（一条命令，单独终端挂着）**
```bash
lens serve          # 本地起服务，浏览器打开 localhost:7878
```

**③ 给工具函数加装饰器（唯一代码改动，函数体一行不改）**
```python
from lens import bind_tool

@bind_tool                      # 普通工具：只记录
def execute_sql(sql: str) -> list[dict]:
    return db.query(sql)

@bind_tool(suspend=True)        # 高危工具：命中即挂起，等人放行
def send_email(to: str, subject: str, body: str):
    smtp.send(to, subject, body)

# 原 agent 循环不动
```

**④ 照常跑**：`python my_agent.py`

**⑤ 运行时**：跑到 `send_email` → 网页弹框（显示 prompt + 工具 + 参数）→ 点【放行/拒绝】；死循环 → 熔断告警 + 抛 `AgentLoopException`；全程 trace 树实时生长，可回看。

## 6. 已确认的产品决策

1. **Thought 采集分层**（决策 1）：装饰器做地基（必须），框架适配器做可选增强（后置）。自研 agent 的 Thought 靠手动 `lens.log_thought()` 埋点。
2. **看板未启动时 agent 必须能跑**（决策 2）：SDK 连得上看板就实时推，连不上则静默降级，绝不因看板未开而崩溃（否则"零配置"破功）。
3. **断点【拒绝】= 返回失败结果，而非抛异常**（决策 3）：让 agent 以为工具执行失败、自行走错误分支继续推理——这是"人机协同"的精髓，debugger 的语义是"逐步替它做决定、看它如何应变"，而非杀掉 agent。

## 7. 架构决策：智能放后端、SDK 变薄协议 client（已确认）

### 7.1 进程分离架构

```
[Agent 进程 —— 任意语言]        [Lens 后端 —— 纯 Python]        [WebUI —— 浏览器]
  Go / TS / Py agent             FastAPI + SQLite + 决策引擎       HTML/JS
```

收集、存储、熔断判定、断点挂起、WebUI 全在后端，**与 agent 语言无关**。依赖语言的只有"探针"层。

### 7.2 核心原则：智能在 SDK → 智能在后端

- 熔断判定、断点挂起决策统一放后端；SDK 只当"极薄协议 client"（发 HTTP + 阻塞等响应 + 抛异常/返回失败）。
- 好处：一份逻辑跨语言共享；每种语言的 SDK 退化为几十行模板代码。

### 7.3 统一决策端点

Loop Breaker 与 Active Breakpoint 统一为同一个端点：

```
每次工具调用前，SDK 同步发请求：
POST /v1/execution-request   { session_id, tool_name, args }

后端三种回复：
  ① { decision: "allow" }                          → 正常，直接执行
  ② { decision: "reject", reason: "loop" }         → 死循环熔断，SDK 抛 AgentLoopException
  ③ 挂起不回复…… 等用户在网页点【放行】→ 回 allow；点【拒绝】→ 回 { decision: "reject", reason: "human" } → SDK 返回失败结果
```

关键结论：**断点不需要 SDK 侧 WebSocket、也不需要 `asyncio.Event`**——SDK 阻塞在一个同步 HTTP 请求上等后端回话即可，所有语言都原生支持。WebSocket 仅用于"后端 ↔ 网页"。

### 7.4 三种语言的探针形态（底层同一协议）

```python
# Python —— 装饰器（语法糖）
@lens.bind_tool
def execute_sql(sql): ...
```

```go
// Go —— wrapper 或显式埋点
func executeSql(sql string) Result {
    r := lens.Before("execute_sql", map[string]any{"sql": sql}) // 阻塞等后端决策
    if r.Decision == "reject" { return Result{Err: r.Reason} }
    // ... 原逻辑
    lens.After(...)
}
```

```ts
// TS —— 装饰器或显式埋点同理
@lens.tool
function sendEmail(to: string, body: string) { ... }
```

## 8. 对 PRD 的修正

| PRD 原文 | 修正 | 理由 |
|---|---|---|
| Loop Breaker：SDK 内部维护滑动窗口 | 滑动窗口 + 相似度判定放后端 | 跨语言不重写逻辑 |
| Active Breakpoint：SDK 内部 asyncio.Event 阻塞 | 改为"挂起的同步 HTTP 请求" | 去语言依赖，天然跨语言 |
| Loop Breaker 与 Breakpoint 分述 | 统一为 `/v1/execution-request` 决策端点 | 一个端点、两个判断分支，更简洁 |

---

## 9. 权衡（tradeoff）

智能放后端 → 每次工具调用多一次本地 HTTP 往返。本地回环微秒级，而死循环烧 Token 是秒级，熔断延迟可忽略；换来"一份逻辑、跨语言共享"。

---

## 10. MVP 范围与下一步

### 资源分配
- **核心 = Active Guardrails**（Loop Breaker + Active Breakpoint），砸力气的地方。
- **支撑 = 最小可用 SDK 探针**：喂给熔断器/断点即可，不做全量 tracing。
- **展示 = 够用的控制面板**：放行/拒绝/熔断告警 + 够用的 trace 树；暗黑好看是加分项。

### 明确不做（dev-time 工具边界）
多租户、权限、生产高可用、团队共享。

### 下一步
1. 细化通信协议：endpoint 清单 + 消息结构（JSON schema）。
2. 落后端骨架（FastAPI + SQLite + 决策引擎）。
3. 落 Python SDK（装饰器 + 薄 client）。
4. Go/TS SDK 后置：加一个薄 client，后端零改动。
