# 工作日志生成（log-generate）

目的：把当前对话的工作内容沉淀为一份 markdown 工作日志，作为用户的**工作记录**和**续接工作的入口**——新对话只读这份文件就应能接上工作。不是评审报告，不是 commit message 复读，是面向未来自己/接手者的交接文档。

## 文件规范

- 目录：`/Users/yu/Documents/workspace/aihelpsai/MicroAgent-Lens/docs/logs/`
- 命名：`YYYYMMDD-项目名-工作主题.md`（日期=对话当天；项目名取仓库/服务名如 `microagent-lens`；主题用短中文短语，如 `hindsight画像精简one-shot样例法`）
- 开头用「**概述**」一节（不用 TL;DR、不用 blockquote），多条时 `1.` `2.` `3.` 逐条编号
- 全文不使用独占一行的 `---` 分隔符，分节靠标题/空行
- 长文档阈值：预估 ≥300 行或 ≥15 KB 必须骨架 + Edit 分段写，禁止单次 Write 全文

## 内容结构（固定六节）

1. **概述**：2-3 条速览——需求一句话、结果（关键数据/commit 号）、当前状态（已提交/未提交/已 push）
2. **前置需求**：本次对话延续的上一需求脉络（版本迭代史、上轮拍板的决策）。纯新需求无前置则写「无前置，本次为首次提出」
3. **工作内容**：做了什么——环境与操作要点、迭代/实验过程（多轮 A/B 用表格：轮次/形态/结果/结论）、关键决策点、验证方式与证据
4. **改动文件**：逐文件列出改了什么（路径 + 变更点），附验证命令与结果（build/test 输出要点）、commit 哈希
5. **出现的问题与结论**：**必须用表格**（用户明确要求的格式）——四列 `# / 问题 / 根因 / 结论·解法`，问题按重要性排序，含「已解决」和「已知残留/暂不做」两类
6. **续接指引**：给接手者的入口——下一步方向、待办、迭代路径（怎么改、改哪里、什么机制生效）、关键 /tmp 留档或产物位置、环境终态

## 写作纪律

- **蒸馏优先于罗列**：问题不只是现象描述，必须带根因和处置——「现象 → 为什么 → 怎么办」三段完整。踩过的坑写清楚教训（如「样例必须展示全部必需要素」这类可复用结论），这是日志的核心价值
- **失败路径也要记**：被否决的方案、负优化的实验轮次、为什么不用——防止未来重踩（对应 stage-handoff 的否决类决策蒸馏原则）
- **数据说话**：实验/优化类工作带上实测数据（改前/改后指标），多轮对比用表格
- **只写本对话相关**：不展开仓库级背景（那是 CLAUDE.md 的职责）；不复制 commit message 全文（链接 commit 哈希即可，正文蒸馏进各节）
- 信息来源：回看本次对话的关键节点 + `git log`/`git diff` 核实改动与提交号——**写 commit 哈希前必须核实**，不凭记忆写
- 中文写作，保留英文术语

## 执行流程

1. `git log`/`git status` 核实本次对话的提交与未提交改动（若在 worktree 注意当前分支）
2. 回顾对话：需求起点 → 前置脉络 → 迭代过程 → 问题与结论 → 最终状态
3. 按六节结构写文件（先估体量决定 Write/Edit 策略）
4. 写完向用户确认落档路径，并提示：若本次工作还有后续阶段，可配合 /stage-handoff 做跨对话交接
